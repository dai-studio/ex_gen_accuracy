Moxy build comparison

Three fresh Claude Code sessions built the same gateway, Moxy, from three forms of input: a one-paragraph prompt, a 205-line prose spec and a 555-line BPMN + dai: spec. This report compares what each run cost with how closely its code follows the specification.

Verdict

The two spec builds are equally accurate, and the .dai build cost 28% less. Scored against the 68 requirements in spec.dai, the source that spec.md was written from, spec_dai scores 93.4% for $8.17 and spec_md 92.6% for $11.31. Neither fails any item.

spec_md loses points where the prose dropped exact names. spec.dai gives record field names (userSub, ownerSub, pkceVerifier…) and the config API paths. spec.md only describes them in words. spec_dai uses the exact names and spec_md invented its own, which costs it six points. On the shared behaviour, spec_md is slightly more complete. Scored only against the prose, it reaches 97.1%.

The one-paragraph prompt was cheapest ($6.77) and least accurate (41.2%). With no spec, it chose TypeScript on Node instead of Rust, Pingora, SvelteKit and redb, and replaced OpenID Connect with password logins. Most of its features exist in a different form, so 40 of 68 items are partial.

Findings

Notable deviations and defects

These come from reading the source. Some fall outside the checklist, such as bugs in behaviour the spec does not mention.

prompt_md

  • Used a different stack: TypeScript on node:http with no dependencies and hand-written HTML. It has no Rust, Pingora, SvelteKit or redb.
  • Replaced OpenID Connect with local username and password logins and JWT sessions. The example config's default credentials are admin/admin.
  • Proxy routes are open by default, where the spec requires an API key.
  • Leaks credentials: the caller's Authorization header is forwarded upstream on routes without auth middleware.
  • Retries 502/503/504 responses on other upstreams, which replays POST requests to models.
  • Resets quotas and rate limits on every config reload.
  • Made /api an OpenAI-compatible model API. The spec's assumptions rule this out.
  • Added features the spec does not ask for, including redact, cors, ip-filter, system-prompt, a statistics dashboard and TLS termination.

spec_md

  • Doesn't use the identifiers in spec.dai: stored records use snake_case with subject and owner, values are wrapped in {v, exp}, and the config API uses /api/config/system and /api/config/middleware?path=.
  • The session cookie's Max-Age is sent once and never refreshed. Sessions slide on the server, but the browser still drops the cookie when the original TTL runs out. spec_dai has the same bug.
  • A ${VAR} in a route path or in version is neither resolved nor rejected.
  • For chunked request bodies, the 413 comes only after the upstream has received part of the body. spec_dai has the same bug.
  • Makes blocking redb calls on Pingora's async worker threads.
  • The timeout applies to each read, not to the whole wait, and connect timeouts are capped at 10s.
  • <server> and <auth> are optional, and the order of top-level elements is not enforced.

spec_dai

  • Shares the cookie Max-Age bug and the late chunked-body 413 with spec_md.
  • Upstream 5xx responses don't take an upstream out of rotation; only connection failures and timeouts do.
  • Doesn't close the KV store on shutdown. The process exits directly after draining requests.
  • Admin writes swap the config in directly instead of going through the watcher's reload path.
  • Doesn't enforce that the destination comes last in a route, and accepts /* as a route path.
  • Builds the OIDC redirect_uri as http://<Host>, so it's wrong behind TLS and trusts the client's Host header.
  • A failed reload's error can stay on screen after the file is fixed, if the fix restores the active content exactly.
  • Grants admin only if the identity provider hasn't marked the email unverified. The spec has no such condition.

Method and limits

How the numbers were produced

  • Cost and tokens come from each folder's stats.md, which stats.py reads from the session transcript's final cost-state record. No subagents or web searches were used in any run.
  • Accuracy uses 68 requirements taken from inputs/spec.dai, the model that spec.md was written from, grouped A–K and listed with their source nodes in requirements.md. Three independent read-only auditors, one per build, scored every item from the source code rather than from NOTES.md.
  • Six items were re-scored against spec.dai's exact identifiers. The first audit used the prose wording. G6, J3, J4, J5, J6 and J9 name API paths and record fields exactly in spec.dai but only in words in spec.md. I checked those items in the code. spec_md moved from pass to partial on all six. spec_dai and prompt_md didn't change. Against the prose wording, spec_md scores 97.1%.
  • One score was normalised. The auditors scored the same chunked-body behaviour differently, so spec_md I4 was changed from pass to partial to match spec_dai. Both builds enforce the limit the same way, and the code was checked.
  • prompt_md never saw the spec. Its score measures how far a build without context lands from the intended design. It does not measure whether the session followed its instructions. A partial for prompt_md usually means the same capability with different names, paths or status codes.
  • There is one run per input, so the 0.8-point gap between the two spec builds is within what a second run could reverse. The $3.14 cost gap could reverse too. Repeating each variant three to five times would separate the effect of the input format from run-to-run noise.
  • Build check. cargo test passed for both Rust builds: 68 + 15 tests for spec_md and 27 + 20 for spec_dai. npm run typecheck, build and test passed for prompt_md (155 tests). The SvelteKit UIs were not rebuilt; their checked-in ui/build output was used.
  • Input drift. outputs/spec_dai/spec.dai differs from inputs/spec.dai in one attribute, workflowMeta version (0.1.0 in the working copy, 0.2.0 in the original). The rest of the content is identical.
